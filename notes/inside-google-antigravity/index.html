Inside Google Antigravity: Coding Agent Anatomy, 3-Tier Memory, and Self-Improving Workflows

How a modern coding agent runs safely, organizes personal and team memory on disk, and improves overnight on Google Cloud without prompt bloat.

Coding agents feel sharp on Monday, then often hit a wall by Friday. Stuffing every chat log into a bigger window slows replies and lowers focus (context rot). Telling the agent to append every bug fix straight to AGENTS.md creates another trap: one-off guesses and conflicting rules pile up and quietly break older tasks.

Picture a routine Tuesday bug on a data team. An agent wraps partitioned event_ts in DATE() inside a BigQuery WHERE clause and hits a 10 GB scan cap. How should the agent run that Tuesday fix safely, and how can it carry that lesson into Thursday's work without turning AGENTS.md into junk?

Figure 1: Tuesday's full-scan bug breaks partition pruning and why naive prompt or history shortcuts fail.

Figure 1 shows the core tension: we want to prevent Tuesday's full-scan bug on future runs without bloating or breaking shared prompts. Answering how starts inside the coding agent itself.

1. How One Task Runs: Google Antigravity's Four Tenets

Research on SWE-agent (arXiv:2405.15793) showed why coding agents struggle with raw bash shells and need a purpose-built Agent-Computer Interface (ACI). Google's official Introducing Google Antigravity post builds on that lesson by bringing "four key tenets of collaborative development together: trust, autonomy, feedback, and self-improvement" (Figure 2):

Figure 2: How Google Antigravity pairs autonomy, inspectable artifacts, inline feedback, and disk-based self-improvement inside one coding session.

1. Autonomy

Antigravity runs multi-step coding work without constant hand-holding:

  • Workspaces and CLI: Agent Manager and the VS Code Editor pair with the headless agy CLI to route live or background tasks.
  • Isolated Subagents: Heavy codebase searches and tests spin out to Subagents with fresh context windows and Git branch worktrees. That keeps noisy logs out of your main chat.
  • OS Sandbox and Browser: Commands run inside an OS-kernel Terminal Sandbox (sandbox-exec on macOS, kernel namespaces/cgroups on Linux) without VM lag. Meanwhile, Chrome Browser-in-the-Loop checks live UI screens.
  • MCP and Lifecycle Hooks: MCP (mcp_config.json) connects tools like BigQuery, while Lifecycle Hooks (hooks.json) block unsafe shell or MCP calls pre-run.

2. Trust (Artifacts)

Rather than hiding work or dumping raw terminal logs from Tuesday's SQL fix, the agent emits structured Artifacts. Engineers inspect a Plan before edits start, then check diffs, screenshots, and a final Walkthrough.

3. Feedback (Live Steering)

If you spot the bad DATE(event_ts) filter inside that Plan, you leave a Google-Docs-style comment right on the Artifact. The agent updates its active run without restarting from scratch.

4. Self-Improvement (Knowledge on Disk)

Antigravity saves architecture notes and reusable subtask steps in Rules and Skills so future sessions learn from past work.

Tenets 1 to 3 keep Tuesday's single task safe, inspectable, and easy to steer. Tenet 4 (Self-Improvement) is where teams hit trouble by Friday. If every fix gets dumped into one flat prompt file, personal notes leak to teammates and prompts grow out of control. Avoiding that trap takes a clear layout on disk.

2. Structuring Self-Improvement on Disk: Three Memory Tiers

Google's May 2026 whitepaper, Context Engineering: Sessions, Memory (Milam, Gulli, & Nawalgaria), gives the blueprint for organizing Tenet 4. First, it splits today's Session workbench from long-term Memory, which curates lessons offline (Ingestion -> Extraction -> Consolidation -> Retrieval) instead of searching static docs like RAG. Second, it separates personal notes from shared team guides, and splits knowing facts from knowing step-by-step workflows.

Applying those whitepaper splits to Google Antigravity pairs built-in files with two custom additions (sessions/ summaries and a team .agents/wiki/) across three disk tiers:

~/.gemini/
  ├── GEMINI.md                        # [Built-in] Tier 2 private user defaults
  ├── config/hooks.json                # [Built-in] PreToolUse & Stop hooks
  ├── config/mcp_config.json           # [Built-in] Approved MCP bridges (BigQuery)
  └── sessions/<id>/summary.json       # [Custom RSI] Tier 1 Stop-hook resume summary
repo/.agents/
  ├── rules/*.md                       # [Built-in] Tier 2 team rules (<= 450 tokens)
  ├── wiki/*.md                        # [Custom RSI] Tier 2 team Markdown wiki
  └── skills/<name>/
        ├── SKILL.md                   # [Built-in] Tier 3 on-demand YAML workflow
        └── scripts/                   # [Custom RSI] Checked scripts from dreaming
  1. Tier 1, Working Session and Monday Resume (Private Workbench): Today's chat, terminal runs, and Artifacts stay in the active session, trimmed mid-task with /context and /compact. When Friday's session closes, one short summary (objective, decisions, next_step) is saved locally with higher weight on recent work. Monday morning resumes cleanly without reloading 50k raw log tokens.
  2. Tier 2, Short Rules and Team Wiki (Knowing Facts): Personal defaults stay private in ~/.gemini/GEMINI.md. Shared rules sit in .agents/rules/*.md, capped at <= 450 tokens per domain inside Antigravity's 20k limit. Deeper system maps live in .agents/wiki/*.md for engineers to read directly, searched with keyword plus vector matching (like Reciprocal Rank Fusion).
  3. Tier 3, Step-by-Step Workflows (Knowing How): Multi-step tasks live in .agents/skills/<name>/SKILL.md alongside helper scripts/. At startup, Antigravity reads only the tiny YAML header, loading full instructions and scripts only when a matching task arrives.

In our BigQuery example, Tuesday's failure turns into compact [PROMOTED] (proven habits) and [DEAD_END] (verified traps) rules in Tier 2:

<!-- .agents/rules/rsi-data-guardrails.md (Always-On, <= 450 tokens) -->
# Data Pipeline Guardrails
 
- [PROMOTED | verified: 14 runs] Validate SQL with `bq query --dry_run` before executing or reporting byte estimates.
- [DEAD_END | verified: 7 runs] Never wrap partitioned `event_ts` in `DATE()` inside `WHERE`; it breaks partition pruning and hits the 10 GB scan cap.
- [DEAD_END | verified: 5 runs] Never retry webhook workers without an `idempotency_key` header; Pub/Sub delivers duplicates.

Meanwhile, the full dry-run workflow stays tucked out of sight in Tier 3 until a BigQuery task matches:

---
name: bq-audit
description: Audit and dry-run BigQuery SQL changes before execution.
---
 
# BigQuery Audit Workflow
 
1. Confirm partition filters compare raw `TIMESTAMP` bounds directly.
2. Run the scan-byte check before reporting costs or querying prod:
   `python3 .agents/skills/bq-audit/scripts/dry_run_gate.py <sql_file>`
3. If the dry-run check fails, fix the raw `TIMESTAMP` filter before running the query.

This three-tier layout gives Tuesday's SQL lesson a clean home on disk. Yet a harder question remains: who writes and updates .agents/rules/ and .agents/skills/, and when?

3. Updating Memory Without Drift: Stage A Session Close vs. Stage B Nightly Dreaming

Letting an agent edit shared .agents/ files mid-task turns single-run guesses into team rules, while full prompt rewrites drop older checks. Recent Recursive Self-Improvement (RSI) research shows a safer pattern. Projects like Darwin Gödel Machine (arXiv:2505.22954) and AlphaEvolve on Google Cloud (arXiv:2506.13131) test code changes offline against automated checks. Meanwhile, GEPA (arXiv:2507.19457), ACE (arXiv:2510.04618), and Sleep-time Compute (arXiv:2504.13171) show why small offline memory updates beat rewriting entire prompts. Using the exact hooks.json, mcp_config.json, and agy CLI tools from Section 1, Figure 3 splits updates into two clean stages:

Figure 3: Separating daytime task execution and session-close logging (Stage A) from nightly Google Cloud batch dreaming and safety-gated pull requests (Stage B).

Stage A: Session-Close Stop Hook (Private, Run Once)

Direct commands from a developer carry the highest trust, so they can update private ~/.gemini/GEMINI.md right away. When Tuesday's session closes, Antigravity's Stop hook in hooks.json summarizes the transcript once for Tier 1 Monday resume. It also logs Tuesday's DATE(event_ts) scan failure (DEAD_END, score, error) to BigQuery via BigQuery MCP (mcp_config.json). Shared .agents/ files stay read-only all day.

Stage B: Nightly "Dreaming" on Google Cloud (50+ Logged Runs)

Off-hours, Cloud Scheduler and Workflows run Batch Inference (Gemini 3.x on Gemini Enterprise Agent Platform) across saved summaries and the BigQuery log table in three steps.

1. It filters noise and merges conflicts. Single-run flukes (N = 1) expire quickly, while repeated traps like DATE(event_ts) (N = 5+) become [DEAD_END] rules. The job also merges conflicting notes across .agents/wiki/*.md and sends compute bottlenecks to AlphaEvolve on Google Cloud.

2. It turns proven rules into scripts. When code can check a [PROMOTED] rule, the job moves it into a script under .agents/skills/bq-audit/scripts/ and trims .agents/rules/.

--- a/.agents/rules/rsi-data-guardrails.md
+++ b/.agents/rules/rsi-data-guardrails.md
@@ -1,4 +1,3 @@
-- [PROMOTED | verified: 14 runs] Validate SQL with `bq query --dry_run` before executing or reporting byte estimates.
+- Checked automatically by `bq-audit` skill (`scripts/dry_run_gate.py`).

3. It runs safety and holdout checks before opening a Git PR. Model Armor scans candidate diffs for prompt attacks (memory poisoning), while Sensitive Data Protection strips PII and secrets. Next, Gen AI Evaluation Service (batch_evaluate()) and Section 1's headless agy CLI test personal defaults, attack blocking, and multi-day quality on an 80/20 holdout split. Only passing diffs open a DRAFT_PROPOSED Git Pull Request for human review.

Once a teammate reviews that overnight pull request and runs git pull, the loop closes on the very next BigQuery task.

4. Closing the Loop: Thursday Morning

Thursday morning shows why connecting these pieces pays off (Figure 4):

Figure 4: After pulling the reviewed PR, compact Tier 2 rules and Tier 3 scripts catch partition mistakes before production execution.

Antigravity's Autonomy, Trust, and Feedback tenets run the new query inside the OS sandbox and present a clear Plan. Self-Improvement loads the tiny [DEAD_END] rule in Tier 2 and pulls bq-audit with dry_run_gate.py on demand from Tier 3. Tuesday's 10 GB scan mistake is caught automatically before hitting production, and shared team prompts stay short week after week.
